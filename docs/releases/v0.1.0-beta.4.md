# Vestiarion v0.1.0-beta.4 — Asana, Pipedrive and a command line

The fourth beta of Vestiarion. Contractor work delivered in Asana is accepted against the milestone's criteria before
the agent pays it. Won deals come in from Pipedrive, and receipts go back to them. Developers and operators can work
with a workspace from a terminal with the `vestiarion` command.

This release covers 7 merged pull requests (#344 to #350) since
[v0.1.0-beta.3](https://github.com/duongnq2798/vestiarion/releases/tag/v0.1.0-beta.3). Each feature was reviewed by an
independent reviewer before merge, and every defect found was fixed with a test that failed first. Production is
deployed from `main` on every merge, so it may already run newer changes than this release lists.

## Highlights

- **Accept contractor work from Asana (#347, #350).** An owner or admin connects Asana in Settings, and a milestone is
  linked to the Asana task its work is delivered in.
  - The milestone holds the acceptance criteria from the agreement, written in Vestiarion, never by Asana.
  - When the task is completed in Asana, the milestone is **ready for acceptance**. A person checks the deliverables
    (the task's attachments and the links in its description and comments) against the criteria and accepts the work.
    Only then is it verified, and the agent decides the payment under every guardrail.
  - A completed task alone never pays. The payee can never accept their own work, matched by email and, where Asana
    can tell, by Asana account.
  - A task reopened, or with changed deliverables, after acceptance takes the acceptance back and holds the milestone
    for review, when Vestiarion reads it before the payment is sent. The task is read before the agent decides, again
    right before it sends the payment (#350, added after a live run on Arc testnet showed a task reopened while the
    agent decided could still be paid), every 15 minutes, and on **Check Asana now**.
  - In a live run on Arc testnet, a task completed in Asana and accepted was paid 5 USDC by the agent and confirmed on
    Arc 3 seconds after it was sent.
- **Deals from Pipedrive, receipts back to them (#345, #349).** An owner or admin connects a Pipedrive company, and its
  won deals come in under Deals with their organizations and persons.
  - **Plan collections** fills in a deal from a won Pipedrive deal: the customer, the title, the value (US dollars as
    USDC, euros as EURC) and the won day.
  - Pipedrive says when a deal changes, and Vestiarion reads it again from Pipedrive itself. A planned deal changed
    there says **Changed in Pipedrive**; nothing changes in Vestiarion until a person does.
  - Once allowed, each planned deal gets what was collected, what is still owed, the last receipt and the
    reconciliation status, in Vestiarion's own deal fields, never over a change someone made there.
  - Payments on Arc testnet or in shadow mode are never written to Pipedrive, which does not mark its sandboxes.
- **A command-line interface (#346).** `@vestiarion/cli` 0.1.0 on npm, built on the TypeScript SDK.
  - `vestiarion login` checks a workspace API key with one read and saves it for the user alone; `whoami` names the
    workspace and its network.
  - It reads bills, invoices, counterparties, milestones, the treasury and the agent's decisions with their reasoning,
    as text or as the API's JSON.
  - It adds records only after showing what it will send and asking, or with `--yes`. It never approves or pays.
  - Offline, it checks an audit export and a webhook delivery's signature. It sends no telemetry.
- **Asana's and Pipedrive's marks (#348)** appear on the landing page, the Settings cards and the connect pages, as
  Xero's, QuickBooks' and HubSpot's do.

## Database

Three new migrations bring the total to 111 (`0001_init.sql` to `0117_pipedrive_ready_org.sql`; numbers 0091 to 0093
and 0096 to 0098 are unused):

| Migration | Adds |
| --- | --- |
| `0115_asana_acceptance.sql` | Asana task links, Asana webhooks, acceptance criteria on milestones, and the two functions that accept work and take an acceptance back |
| `0116_pipedrive_connector.sql` | Pipedrive on the connector core and the receipts outbox, one Pipedrive company per workspace, and a readiness check |
| `0117_pipedrive_ready_org.sql` | Pipedrive's readiness check, taking the workspace as every other check does |

All are additive and idempotent, and are applied in filename order by `npm run db:migrate`. Publishing a release never
runs migrations.

## Known limitations

- **Beta.** Screens, wording and features change often. The spending-limit and escrow contracts have not been audited.
- **Asana webhooks.** On the live deployment Asana has so far refused to make the webhook on a linked task, so a change
  in Asana is read before the agent decides, right before it pays, every 15 minutes and on **Check Asana now**, not yet
  within a minute. Asana's reason is now logged and is being looked into.
- **Asana reads fail open.** While Asana cannot be read, an acceptance stands as the person gave it; a task reopened
  then is seen at the next read that succeeds, which may come after the payment.
- **Pipedrive** does not mark sandbox companies, so receipts are written only for payments on Arc mainnet.
- **QuickBooks Online** still connects to sandbox companies only, until Intuit's app assessment is complete.
